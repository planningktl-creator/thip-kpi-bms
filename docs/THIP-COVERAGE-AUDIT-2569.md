## 5. ข้อบกพร่องที่พบจากการตรวจสอบ (มีหลักฐานรันจริง)

### 5.1 รหัส ICD เขียนผิดรูปแบบ — ตัวกรองไม่มีทาง match (ร้ายแรง)

ที่เก็บจริงของ `an_stat.pdx` / `iptdiag.icd10` เป็นแบบไม่มีจุดและมักยาว 4 หลัก (เช่น `A150`, `C509`, `I210`)
การเทียบด้วยลิสต์รหัส 3 หลักตรง ๆ จึงได้ศูนย์ ยกเว้นกรณีที่เก็บเป็น 3 หลักพอดี

| รหัส | ไฟล์:บรรทัด | ปัญหา | หลักฐานรันจริง FY2569 |
| --- | --- | --- | --- |
| DR0201 | `src/services/queryRegistry.ts:51` | `pdx IN ('A15','A16')` | as-written = **0** · แก้เป็น `LEFT(pdx,3)` = **137** |
| DC0401 | `src/services/queryRegistry.ts:50` | ลิสต์มะเร็งเป็นรหัส 3 หลัก (C00–C97, D00–D09) | as-written = **123** · แก้เป็น LEFT 3 = **610** |
| DC0403 | `src/services/thipFamilies/maternal_specialty.ts:142-147` | `LEFT(pdx,3) IN ('C220',...)` — LEFT 3 หลักเทียบรหัส 4 หลัก ไม่มีทางตรง | ตัวหาร = 0 ทุก 12 เดือน · แก้เป็น C22 = **81** |
| CM0104 / CM0105 / CM0118 / CM0119 | `queryRegistry.ts:53` (`csWhere`), ใช้ที่ 528/529 และในไฟล์ CM0118/CM0119 | ลิสต์ `pdx IN ('O820','O821','O822','O828','O829','O842')` และ iptoprt icd9 `74.x` ได้ตัวเศษ 0 ทุกงวด (CM0104/CM0105 ตัวหารก็เป็น 0 ทุกงวด · CM0118/CM0119 ตัวหาร 235 ตัวเศษ 0) | หลักฐานชี้ว่ารูปแบบรหัส O-อื่นใช้ได้ (O244 ตรง 149 ครั้ง) แต่ O82x ไม่มีในข้อมูลเลยทั้ง 12 เดือน — ต้องยืนยันว่า รพ. ลงรหัสผ่าตัดคลอดแบบใด (O82x / icd9 74.0-74.2 / ใช้ labor table) แล้วปรับตัวกรองให้ตรง |

ผลกระทบ: รายงานของ DC0401 ต่ำกว่าจริงราว 5 เท่า (123 → 610 เมื่อแก้ช่วงข้อมูลเดียวกัน), DR0201 และ DC0403 รายงานเป็น 0

หมายเหตุ: DG0201 (`pdx IN ('K35','K352','K353','K358')`) แม้มีรหัส 3 หลักปนอยู่ แต่ลิสต์มีรหัส 4 หลัก (`K352`/`K353`/`K358`) ครบ จึง match ได้จริง —
หลักฐานรันจริง: ตัวหารรวม 253 ราย ตัวเศษรวม 46 ราย (ใช้ได้ ไม่ต้องแก้)

### 5.2 ความไม่สอดคล้องที่ควรยืนยัน

- AA0105 ลิสต์ `pdx IN ('I10','I110','I119')` ครอบคลุม I10/I11.0/I11.9 แต่ไม่ครอบ I11 (ไม่มีจุด) และ I11.1–I11.8
- AA0104 ลิสต์ E10.0/.1/.6/.9, E11.0/.1/.6/.9, E13.x, E14.x — ต้องเทียบกับ token ในพจนานุกรม PDF อีกครั้ง
- 4 รหัสรายปี (HC0101, HC0102, HH0104.3, HH0104.4) เป็น borderline: รอบที่สำเร็จใช้เวลา 6.5–9.9 วินาที และคืนค่าได้ (ค่าอยู่ในไฟล์ live แล้ว)
  แต่รอบ adaptive ล่าสุดถูกตัดที่เพดาน ~10 วินาที (HTTP 404) และเป็นรายปีจึงแบ่งหน้าต่างเวลาไม่ได้ → สถานะรายงานเป็น "ยังไม่มี"
  ต้องลดภาระ query ให้ต่ำกว่าเพดานเพื่อให้ได้ผลสม่ำเสมอ
- CS0401 ใน PDF = พิมพ์ผิดที่หัวกระดาษของหน้า DS04 (เนื้อหาข้างใต้คือ DS0401 กลุ่ม Opioid) — พจนานุกรม 232 รหัสครบถ้วน
- ข้อจำกัดการตรวจ: ช่วงท้ายของการตรวจ BMS tunnel ตอบ 502 ทำให้ probe ยืนยันสดบางรายการ (รูปแบบ O8x/K35/C22 ในฐานข้อมูลจริง,
  DC0401 แบบ Pdx หรือ Sdx, labor/iptoprt ของการผ่าตัดคลอด) ยังไม่ครบ — มีสคริปต์ `tmp/probe_pending_confirmations.py` รอ retry อัตโนมัติ

## 8. การกำหนดปีงบประมาณด้วยค่าเดียว (ปรับปรุง 25 ก.ย. 2569)

เดิมทุกคำสั่งรับ bind parameter สองตัว (`:start_date`, `:end_date`) ผู้ใช้ต้องคำนวณเองว่า
ปีงบ 2569 = 2025-10-01 ถึง 2026-09-30 ตอนนี้ **ใส่ปี พ.ศ. ค่าเดียว** แล้วช่วงวันคำนวณให้เอง

กลไก: ทุกคำสั่งมี CTE ชื่อ `thip_params` อยู่ต้นคำสั่ง

```sql
WITH thip_params AS (
  SELECT
    v.fiscal_year,
    make_date(v.fiscal_year - 544, 10, 1) AS fy_start,   -- 1 ต.ค. ของปีที่เริ่ม
    make_date(v.fiscal_year - 543, 10, 1) AS fy_end      -- 1 ต.ค. ปีถัดไป (ขอบเขตบนแบบไม่รวม)
  FROM (VALUES (2569)) AS v(fiscal_year)                 -- <<< แก้ปีงบที่บรรทัดนี้ที่เดียว
)
```

- `:start_date` → `(SELECT fy_start FROM thip_params)`
- `:end_date` → `(SELECT fy_end FROM thip_params)` (คงลักษณะ **exclusive** เดิม → วันสุดท้ายที่รวมคือ 30 ก.ย.)
- `:fiscal_year` → `(SELECT fiscal_year FROM thip_params)`
- ภาคผนวก A (สคริปต์หลายคำสั่ง) ที่ใช้ `DELETE ... WHERE fiscal_year = :fiscal_year` ซึ่งอ้าง CTE ไม่ได้
  จะถูกแทนด้วย literal ที่คำนวณจากปีเดียวกัน จึงยังแก้ปีที่จุดเดียวได้

ตัวอย่างการคำนวณ (ยืนยันด้วยการรันบน PostgreSQL จริง):

| ปีงบ (พ.ศ.) | เริ่ม | วันสุดท้ายที่รวม | ขอบเขตบนไม่รวม |
| --- | --- | --- | --- |
| 2569 | 2025-10-01 | 2026-09-30 | 2026-10-01 |
| 2570 | 2026-10-01 | 2027-09-30 | 2027-10-01 |
| 2571 | 2027-10-01 | 2028-09-30 | 2028-10-01 |

### หลักฐานว่าการแก้ไม่กระทบผลลัพธ์

1. **เทียบรูปแบบเดิมกับรูปแบบใหม่บนตารางเดียวกัน** — รันคำสั่ง 10 ตัว (ทั้ง HOSxP และ external)
   ทั้งแบบเดิม (แทน `:start_date`/`:end_date` ด้วย literal) และแบบใหม่ (ใส่ปีงบ) แล้วเทียบ
   **ทุกคอลัมน์ของทุกแถว** → เหมือนกันทุกประการ 10/10 คำสั่ง (`tmp/prove_params_equivalence.py` → PASS)
2. **เปลี่ยนปีแล้วผลเลื่อนจริง** — รันคำสั่งเดียวกับปีงบ 2569 → `period_start` = 2025-10-01;
   แก้เฉพาะเลขปีเป็น 2570 → `period_start` = 2026-10-01 (`tmp/prove_fiscal_year_live.py` → PASS)
3. **ตัวตรวจทั้งชุด** — ไม่มี bind token วันที่เหลือในโค้ด (0), ทุกบล็อกที่ใช้ปีงบมี CTE ครบ 256/256 บล็อก,
   ค่า `(2569)` ที่ต้องแก้เท่ากับจำนวน CTE (256), pglast parse 260/260 ผ่าน → **bundle PASS**

หมายเหตุ: คอลัมน์ `fiscal_year` ในผลลัพธ์ยังคงค่าตามสาขาข้อมูลเดิมของ repo (ปี ค.ศ. ของสาขา fact เช่น 2026 สำหรับปีงบ 2569)
— การแก้ครั้งนี้ **ไม่เปลี่ยนความหมายคอลัมน์นี้** พิสูจน์แล้วด้วยข้อ 1

## 9. แก้ปัญหา WIN874 ที่ตรวจพบจาก client จริง (25 ก.ย. 2569)

### อาการที่พบ (จาก log ของ Navicat)

``` 
ERROR: character with byte sequence 0xe2 0x89 0xa5 in encoding "UTF8"
       has no equivalent in encoding "WIN874"
```

`0xe2 0x89 0xa5` = `≥` (U+2265) — และบรรทัดก่อนหน้าชี้ไปที่

```
U&'\0064\0075\006C\0074\0020\0061\0067\0065\0064\0020\2265\0020...'
```

คือข้อความ `adult aged ≥ 60 years old` ใน **ชื่อตัวชี้วัดภาษาอังกฤษ** ของรหัส **DC0108.1**

### ต้นเหตุที่แท้จริง (ไม่ใช่เรื่องไฟล์เป็น UTF-8)

การ escape ไฟล์ให้เป็น ASCII ด้วย `U&'\XXXX'` แก้ได้แค่ทิศทาง **ขาเข้า** (ข้อความ Thai
ที่ client ต้องส่ง) แต่ **ค่าที่ query คืนออกมาก็ต้องส่งกลับผ่าน client ให้ได้ด้วย**

ถ้าผลลัพธ์มีอักขระที่ cp874 แทนไม่ได้ (เช่น `≥`) เซิร์ฟเวอร์จะล้มด้วยข้อความข้างบน
ทั้ง ๆ ที่ไฟล์บนดิสก์เป็น ASCII ล้วน — เพราะ `U&'\2265'` ยัง**คืนค่าเป็น `≥`** อยู่ดี

**4 รหัสที่กระทบ:** `DC0108.1`, `DC0201.2`, `HH0101.1`, `HH0101.2` (ชื่ออังกฤษมี `≥`)
และไฟล์รวมที่บรรจุทั้ง 4 รหัส: ชุดรวม 177, ชุดรวม 232, กลุ่มงาน DM_HT

### การแก้

เพิ่ม `repair_escaped_values()` — เขียน `\2265` → `>=`, `\00B7` → `-` ฯลฯ
**ภายใน literal ที่ escape ไว้แล้ว** ผลลัพธ์เป็นค่าเดียวกับที่ `sanitize()` สร้างจากข้อความดิบ
(พิสูจน์แล้วด้วยการรันจริง: ทั้งสองรูปแบบคืนค่าตัวอักษรเหมือนกันทุกตัว และรูปแบบใหม่รันผ่าน WIN874)

ลำดับการสร้างไฟล์ใน builder: `parameterize` → `with_name_columns` → `escape_literals`
→ **`repair_escaped_values`** → `sanitize`
