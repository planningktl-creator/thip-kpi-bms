## 5. ข้อบกพร่องที่พบจากการตรวจสอบ (มีหลักฐานรันจริง)

### 5.1 รหัส ICD เขียนผิดรูปแบบ — ตัวกรองไม่มีทาง match (ร้ายแรง)

ที่เก็บจริงของ `an_stat.pdx` / `iptdiag.icd10` เป็นแบบไม่มีจุดและมักยาว 4 หลัก (เช่น `A150`, `C509`, `I210`)
การเทียบด้วยลิสต์รหัส 3 หลักตรง ๆ จึงได้ศูนย์ ยกเว้นกรณีที่เก็บเป็น 3 หลักพอดี

| รหัส | ไฟล์:บรรทัด | ปัญหา | หลักฐานรันจริง FY2569 |
| --- | --- | --- | --- |
| DR0201 | `src/services/queryRegistry.ts:51` | `pdx IN ('A15','A16')` | as-written = **0** · แก้เป็น `LEFT(pdx,3)` = **137** |
| DC0401 | `src/services/queryRegistry.ts:50` | ลิสต์มะเร็งเป็นรหัส 3 หลัก (C00–C97, D00–D09) | as-written = **123** · แก้เป็น LEFT 3 = **610** |
| DC0403 | `src/services/thipFamilies/maternal_specialty.ts:142-147` | `LEFT(pdx,3) IN ('C220',...)` — LEFT 3 หลักเทียบรหัส 4 หลัก ไม่มีทางตรง | ตัวหาร = 0 ทุก 12 เดือน · แก้เป็น C22 = **81** |
| CM0104 / CM0105 / CM0118 / CM0119 | `queryRegistry.ts:53` (`csWhere`), ใช้ที่ 528/529 และในไฟล์ CM0118/CM0119 | ลิสต์ `pdx IN ('O820','O821','O822','O828','O829','O842')` และ iptoprt icd9 `74.x` ได้ตัวเศษ 0 ทุกงวด (CM0104/CM0105 ตัวหารก็เป็น 0 ทุกงวด · CM0118/CM0119 ตัวหาร 235 ตัวเศษ 0) | หลักฐานชี้ว่ารูปแบบรหัส O-อื่นใช้ได้ (O244 ตรง 149 ครั้ง) แต่ O82x ไม่มีในข้อมูลเลยทั้ง 12 เดือน — ต้องยืนยันว่า รพ. ลงรหัสผ่าตัดคลอดแบบใด (O82x / icd9 74.0-74.2 / ใช้ labor table) แล้วปรับตัวกรองให้ตรง |

ผลกระทบ: รายงานของ DC0401 ต่ำกว่าจริงราว 5 เท่า (123 → 610 เมื่อแก้ช่วงข้อมูลเดียวกัน), DR0201 และ DC0403 รายงานเป็น 0

หมายเหตุ: DG0201 (`pdx IN ('K35','K352','K353','K358')`) แม้มีรหัส 3 หลักปนอยู่ แต่ลิสต์มีรหัส 4 หลัก (`K352`/`K353`/`K358`) ครบ จึง match ได้จริง —
หลักฐานรันจริง: ตัวหารรวม 253 ราย ตัวเศษรวม 46 ราย (ใช้ได้ ไม่ต้องแก้)

### 5.2 ความไม่สอดคล้องที่ควรยืนยัน

- AA0105 ลิสต์ `pdx IN ('I10','I110','I119')` ครอบคลุม I10/I11.0/I11.9 แต่ไม่ครอบ I11 (ไม่มีจุด) และ I11.1–I11.8
- AA0104 ลิสต์ E10.0/.1/.6/.9, E11.0/.1/.6/.9, E13.x, E14.x — ต้องเทียบกับ token ในพจนานุกรม PDF อีกครั้ง
- 4 รหัสรายปี (HC0101, HC0102, HH0104.3, HH0104.4) เป็น borderline: รอบที่สำเร็จใช้เวลา 6.5–9.9 วินาที และคืนค่าได้ (ค่าอยู่ในไฟล์ live แล้ว)
  แต่รอบ adaptive ล่าสุดถูกตัดที่เพดาน ~10 วินาที (HTTP 404) และเป็นรายปีจึงแบ่งหน้าต่างเวลาไม่ได้ → สถานะรายงานเป็น "ยังไม่มี"
  ต้องลดภาระ query ให้ต่ำกว่าเพดานเพื่อให้ได้ผลสม่ำเสมอ
- CS0401 ใน PDF = พิมพ์ผิดที่หัวกระดาษของหน้า DS04 (เนื้อหาข้างใต้คือ DS0401 กลุ่ม Opioid) — พจนานุกรม 232 รหัสครบถ้วน
- ข้อจำกัดการตรวจ: ช่วงท้ายของการตรวจ BMS tunnel ตอบ 502 ทำให้ probe ยืนยันสดบางรายการ (รูปแบบ O8x/K35/C22 ในฐานข้อมูลจริง,
  DC0401 แบบ Pdx หรือ Sdx, labor/iptoprt ของการผ่าตัดคลอด) ยังไม่ครบ — มีสคริปต์ `tmp/probe_pending_confirmations.py` รอ retry อัตโนมัติ

## 7. หลักฐานระดับตาราง — ทำไม cohort ถึงเป็นศูนย์ (นับแถวจริงผ่าน BMS API, 23 ก.ย. 2569)

ตารางว่างทั้งฐานข้อมูล (0 แถว) → ตัวชี้วัดที่พึ่งตารางเหล่านี้ไม่มีทางออกผลจาก HIS ปัจจุบัน:
- `psych_plan` = 0, `psych_therapy` = 0, `psych_assess_head` = 0 → จิตเวชเด็ก/พัฒนาการ (DM0101-DM0302, CP0101, CP0201)
- `tb_register_visit` = 0, `clinicmember_tb` = 0, `arv_lab` = 0 → วัณโรค/เอชไอวี (DR0203-DR0205)
- `opdscreen_pregnancy` = 0, `operation_anes_problem` = 0

ฟิลด์ที่ไม่มีข้อมูลถูกบันทึกในปีงบ 2569:
- `opdscreen.checkup = '1'` → 0 แถว → HE0101-HE0106 (ตรวจสุขภาพประจำปี) ไร้แหล่งข้อมูล
- `opdscreen.advice1..advice7 = 'Y'` → 0 แถว (ทั้งตารางมี 759,348 แถว) → คำแนะนำเลิกบุหรี่/สุขศึกษา (DH0105, DR0103, DN0105) ไร้แหล่งข้อมูลจริง (คำแนะนำอาจถูกเก็บใน `opdscreen_advice` คนละรูปแบบ — มีเพียง 255 แถวใน `opdscreen_advice_item`)
- `operation_list.operation_check_date` = 0 แถว และ `re_operation = 'Y'` = 0 แถว → CO0101 (surgical safety checklist), CO0105, CO0107 ไร้แหล่งข้อมูล
- `er_regist.do_stroke_needle = 'Y'` → 6 แถว → DN0110 มี cohort น้อยมาก (ไม่ใช่ศูนย์)

ตารางที่มีข้อมูล (ยืนยันว่า branch เข้าถึงได้): `opdscreen_advice` 759,348 · `clinic_visit` 84,318 · `ovst_vaccine` 25,544 · `person_anc` 2,653 · `ipt_labour_infant` 1,910 · `er_oper_code` 1,676 · `person_wbc` 1,655 · `clinic_ckd_member_visit` 44 · `operation_emergency` 3 · `operation_visit_list` 2

หมายเหตุ: `opitemrece` ทั้งปีและ 3 เดือนตอบ 404 ที่ ~10.6 วิ — ยืนยันเพดานเวลา ~10 วินาทีของ endpoint (สาเหตุกลุ่ม query-too-heavy)

ข้อจำกัดที่เหลือ: รอบ retry ยืนยันรูปแบบรหัสตรงตัว (I10/C50/K35 exact, รูปแบบ O8x, labor/iptoprt, DC0401 Pdx+Sdx) ล้มเหลว —
สคริปต์ `tmp/probe_pending_confirmations.py` วน retry 60 รอบ ตลอด ~28 นาที แล้วได้ handshake=200 แต่ `POST /api/sql` ตอบ **502 ทุกครั้ง** และจบด้วย `TUNNEL_DOWN`
สรุป: tunnel ของ BMS (10929-F446.tunnel.hosxp.net) ขัดข้องช่วงท้ายการตรวจ — เมื่อ tunnel กลับมาให้รันสคริปต์ซ้ำเพื่อปิดรายการยืนยันที่เหลือ
